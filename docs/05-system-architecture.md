## 2. مكونات النظام ومسؤولية كل مكون

| المكون | المسؤولية | التقنية المقترحة |
|---|---|---|
| **تطبيق الموبايل (Android)** | واجهة المالك والعامل، تخزين محلي Offline-first، منطق عدّاد التجربة المحلي، مزامنة دورية، تبديل الحسابات المحلي | **Flutter** (قرار معتمد — النقطة 12 مغلقة) + SQLite محلي |
| **Central Backend Server** | REST API، منطق الأعمال، المصادقة والصلاحيات، خدمة المزامنة وحل التعارضات، إدارة الاشتراكات/التراخيص، توليد التقارير، إرسال FCM | **NestJS (Node.js + TypeScript) + Prisma ORM** (قرار معتمد — النقطة 13 مغلقة) |
| **قاعدة البيانات** | تخزين مركزي متعدد المستأجرين لكل بيانات النظام (POS + ترخيص + اشتراكات + أجهزة + رسائل + تدقيق) | PostgreSQL |
| **تخزين الملفات** | صور مرفقات الإيداع، صور التالف، ملفات التقارير/كشوف الحساب المولَّدة، نسخ احتياطية سحابية، صور الرسائل/الإعلانات | تخزين كائنات متوافق S3 أو مكافئ |
| **Firebase Cloud Messaging** | إرسال Push حقيقي لتنبيه اقتراب/انتهاء التجربة أو الاشتراك | Firebase Admin SDK من جهة الخادم، FCM SDK من جهة التطبيق |
| **Admin Portal** | تطبيق ويب منفصل تماماً عن تطبيق المتجر، لإدارة الاشتراكات/الأجهزة/الرسائل/سجل التدقيق/الإعدادات | تطبيق ويب يستهلك نفس الـ REST API بصلاحيات `PLATFORM_ADMIN` فقط |
| **الموقع التعريفي العام** | تعريف بالتطبيق، تحميل APK، تواصل — لا يتصل بأي بيانات متجر ولا بوابة دفع | موقع ثابت/CMS خفيف |

## 3. حدود كل مكون (Boundaries)

```text
Mobile App (Owner)  ──┐
                       ├──▶  Central Backend API  ◀── Admin Portal (App Owner فقط)
Mobile App (Worker) ──┘            │
                                    ├──▶ PostgreSQL (كل البيانات، معزولة بـ store_owner_id)
                                    ├──▶ File Storage
                                    └──▶ Firebase Admin SDK ──▶ FCM ──▶ تطبيقات الموبايل

Marketing Website  ──▶  (مستقل تماماً عن Backend التشغيلي؛ اتصال وحيد مسموح: جلب ملف APK من تخزين ملفات ثابت/CDN مستقل عن الـBackend)
```

- لا يوجد اتصال مباشر بين تطبيق المالك وتطبيق العامل — كل تبادل بيانات يمر عبر `Central Backend Server` فقط.
- Admin Portal لا يملك وصولاً تشغيلياً لتفاصيل POS لأي متجر — فقط بيانات الترخيص/الأجهزة/الاشتراكات/الرسائل/التدقيق.
- الموقع التعريفي معزول منطقياً عن كل أنظمة المصادقة والبيانات الداخلية.

## 4. تدفق البيانات (Data Flow) — السيناريوهات الأساسية

### 4.1 عملية بيع (Offline → Sync)
```text
Worker يفتح شاشة SELL (بلا إنترنت)
      │
      ▼
يُدخل الصنف/الكمية/طريقة الدفع → تأكيد
      │
      ▼
تُحفظ العملية محلياً في SQLite الجهاز + تحديث المخزون المحلي + زيادة عدّاد العمليات المحلي
      │
      ▼ (عند توفر إنترنت، ضمن المزامنة الدورية)
Sync Engine يرسل العمليات المحلية غير المُزامَنة إلى Central Backend API
      │
      ▼
الخادم يتحقق: حالة الاشتراك، سقف الائتمان، صلاحيات العامل، يعتمد أعلى قيمة موثوقة لعدّاد التجربة، ينشئ قيود المحاسبة
      │
      ▼
الخادم يرد بنتيجة المزامنة → يُحدِّث حالة العملية محلياً
```

### 4.2 تفعيل اشتراك
```text
Store Owner يتواصل هاتفياً/واتساب مع App Owner
      │
      ▼
App Owner يبحث برقم هاتف Store Owner في Admin Portal
      │
      ▼
يختار نوع الاشتراك ويفعّله
      │
      ▼
Central Backend ينشئ سجل subscriptions جديد، يحدّث store_owners.status = ACTIVE
      │
      ▼ (عند أول مزامنة لتطبيق المالك/عمّاله)
التطبيق يسحب حالة الاشتراك الجديدة ويرفع القفل
```

### 4.3 انتهاء الاشتراك/التجربة → القفل الشامل
```text
الخادم (Scheduled Job دوري) يفحص subscriptions.expires_at وtrial_sales_used/limit
      │
      ▼
store_owners.status = EXPIRED أو TRIAL_EXPIRED
      │
      ▼ (فوري عبر FCM + مضمون لاحقاً عبر أول مزامنة Pull)
Mobile App (Owner + كل Workers) يستقبل الحالة الجديدة → قفل كامل
```

### 4.4 البيع الاضطراري
```text
المالك يحدد مسبقاً سياسة سعر اضطراري لكل صنف (items.emergency_price_mode)
      │
      ▼ (أثناء البيع، أي بائع)
البائع يفعّل "بيع اضطراري" في شاشة SELL → يعدّل الكمية/السعر يدوياً + سبب إلزامي
      │
      ▼
POST /sales (is_emergency_sale=true) → الخادم يتحقق السعر يطابق السياسة
      │
      ├─ لا يطابق → رفض فوري (400)
      └─ يطابق → خصم المخزون + قيد بيع + قيد خسارة منفصل إن وُجد فرق
                        │
                        ▼
                 توسيم العملية is_emergency_sale=true في OPERATIONS_LOG
```

### 4.5 التحكم بالتزامن ومنع البيع الزائد
```text
طلبا بيع متزامنان على نفس الصنف
      │
      ▼
BEGIN TRANSACTION + SELECT items.quantity ... FOR UPDATE
      │
      ▼
أول طلب يصل فعلياً يُخصم وتُحرَّر المعاملة (COMMIT)
      │
      ▼
الطلب الثاني يقرأ القيمة المحدَّثة بعد تحرّر القفل → إن لم تَعُد كافية → 409 INSUFFICIENT_STOCK فوراً
```
تفصيل كامل مع مثال رقمي في `12-business-logic.md`.

## 5. الخدمات الداخلية والخارجية

### داخلية
- **Auth Service** — تسجيل دخول/خروج، إدارة جلسات، أدوار وصلاحيات، كلمات مرور احتياطية مؤقتة، دخول الأدمن + MFA.
- **Sync Service** — استقبال/دمج بيانات Offline، منع التكرار (`sync_operations`)، حل تعارضات (أعلى قيمة موثوقة لعدّاد التجربة تحديداً)، إجبار تحديث التطبيق (`min_app_version`).
- **Subscription/License Service** — إدارة حالة الاشتراك/التجربة، القفل التلقائي.
- **POS Domain Services** — البيع والمخزون والأصناف والتالف والمطابقة اليومية.
- **Credit Service** — الآجل (عملاء، ديون، دفعات، كشوف حساب).
- **Workers Service** — إدارة العمال، العامل المسؤول، موافقات الإنشاء (R-33).
- **Backup Service** — النسخ الاحتياطي السحابي، التحقق من `tenant_binding_hash`.
- **Dashboard Service** — تجميع أرقام لوحة الرئيسية بين تطبيقات المالك والعمال (`GET /dashboard/summary`).
- **Rejected Transactions Service** — حفظ ومعالجة عمليات البيع المرفوضة (R-30).
- **Accounting Service** — توليد قيود القيد المزدوج تلقائياً (بما فيها قيود الإقفال)، حساب الأرباح/الخسائر.
- **Reporting Service** — توليد تقارير وكشوف حساب PDF/Excel.
- **Broadcast Service** — إدارة ونشر الرسائل/الإعلانات/العروض.
- **Audit Service** — تسجيل كل العمليات الحساسة في `audit_log`.
- **Device/License Integrity Service** — بصمة الجهاز، كشف محاولات التحايل.

### خارجية
- **Firebase Cloud Messaging** — تنبيه تجربة/اشتراك فقط.

## 6. مبدأ العزل متعدد المستأجرين (Multi-Tenancy Isolation)

- كل `store_owner_id` يمثل Tenant مستقلاً تماماً (لا فروع، علاقة 1:1 بين المالك والمتجر).
- كل استعلام على بيانات تشغيلية في الخادم يُقيَّد إلزامياً بـ `store_owner_id` المستخرج من هوية المستخدم المصادَق عليه، وليس من أي قيمة يرسلها الطلب نفسه.
- عزل العمال ضمن نفس المالك: كل استعلام ببيانات عامل يُقيَّد أيضاً بـ `worker_id` المطابق لهوية الطالب نفسه عند كون الطالب عاملاً، أو بأي `worker_id` ضمن نفس `store_owner_id` عند كون الطالب هو المالك.

## 7. استراتيجية العمل دون اتصال (Offline-First)

- التطبيق يحتفظ بقاعدة بيانات محلية كاملة الوظائف لتنفيذ كل عمليات POS دون أي اعتماد على الإنترنت لحظياً.
- عدّاد التجربة يُحسب ويُطبَّق قفله محلياً حتى بدون إنترنت.
- المزامنة تحدث: تلقائياً عند توفر إنترنت دورياً (مرتين يومياً على الأقل)، عند فتح التطبيق، أو يدوياً إن وُجد زر مخصص.
- عند تعارض بيانات بين نسخة محلية ونسخة الخادم: يُطبَّق مبدأ "القيمة الأعلى الموثوقة" لعدّاد التجربة؛ لبقية البيانات التشغيلية تُحسم آلية الدمج بالتفصيل في `12-business-logic.md`.

# 09 — Mobile App (Android)

مرجع: `SCREEN_SPEC.md` (31 شاشة/حالة)، `05-system-architecture.md`، `00-RESOLVED-DECISIONS.md`.

---

## 1. البنية العامة
- تخزين محلي كامل (SQLite) يعكس بنية `DATABASE_DESIGN.md` التشغيلية (items, sales, credit_customers, daily_closings...) لدعم Offline-first.
- طبقة Sync Engine منفصلة منطقياً (انظر `12-business-logic.md` القسم 1) تدير قائمة انتظار العمليات غير المُزامَنة (`client_op_id` لكل عملية).
- حالة مصادقة متعددة: يخزّن التطبيق **أكثر من زوج توكنات** (واحد لكل حساب محفوظ محلياً)، مع مؤشر "الحساب النشط حالياً" يحدد أي بيانات محلية تُعرض.

## 2. التنقل (Navigation)
- شريط تنقل سفلي (5 عناصر: أموال، سجل، مباع، مخزون، بيع) في كل الشاشات التشغيلية الرئيسية، **مُفلتراً حسب الدور** — زر "أموال" يظهر للمالك والعامل المسؤول فقط ويُحذف لشريط العامل العادي (BR-010)؛ والشريط كله غائب فقط في `LOGIN`/`SIGNUP`.
- قائمة جانبية (☰) تضم: روابط ثانوية (المصروفات، التقارير، إدارة العمال، معالجة العمليات المرفوضة، النسخ الاحتياطي) + (للمالك فقط) قسم "تبديل الحسابات" أسفلها تماماً.
- محتوى القائمة الجانبية والشريط السفلي **يُفلتَر ديناميكياً** حسب الدور (مالك/عامل مسؤول/عامل عادي) والصلاحيات الفردية — لا عناصر معطَّلة مرئية لوظيفة ممنوعة، بل إخفاء تام.

## 3. إدارة الحالة (State)
- حالة الجلسة: `logged_out | logged_in_normal | must_change_password | account_locked (TRIAL_EXPIRED/EXPIRED/SUSPENDED — الرسالة حسب reason من الخادم)`.
- حالة الاتصال: `online | offline` تُعرض كمؤشر بصري صغير دائم (مثلاً أيقونة أعلى الشاشة) دون حجب الاستخدام.
- حالة المزامنة: `idle | syncing | sync_failed` — لا تحجب واجهة المستخدم (Non-blocking Background Sync).

## 4. التحقق من المدخلات (Validation) على مستوى التطبيق
طبقة أولى من التحقق تحدث محلياً فوراً (قبل أي اتصال خادم) لتجربة استخدام سريعة، مطابقة لقواعد `14-validation-error-handling.md` (قادم في هذه الدفعة)، مع إعادة نفس التحقق إلزامياً على الخادم (لا يُعتمد على التحقق المحلي وحده أمنياً).

## 5. تكامل API
كل الشاشات تستهلك REST API الموثَّق في `API_SPEC.md`/`openapi.yaml`، عبر طبقة Repository محلية تدمج بيانات SQLite المحلية مع استجابات الخادم عند المزامنة.

## 6. حالات التحميل والفراغ (Loading & Empty States)
- كل قائمة (مخزون، سجل عمليات، عملاء آجل...) تحتاج: حالة تحميل (Skeleton/Spinner)، حالة فارغة (رسالة + أيقونة ودّية، مثل "لا توجد عمليات بعد اليوم")، حالة خطأ (مع زر "إعادة المحاولة").
- **(غير موثّقة بصرياً في الصور الأصلية الـ31 — تحتاج تصميماً إضافياً متسقاً مع الهوية عند التنفيذ الفعلي.)**

## 7. التفاعلية المطلوبة (بطاقات تفاعلية أنيقة)
كل إجراء مستخدم (بيع ناجح، حفظ تعديل، حذف، تفعيل/إيقاف) يُقابَل برد فعل بصري: رسالة نجاح عابرة (Snackbar/Toast بأسلوب بطاقة)، أو بطاقة تأكيد تفصيلية عند الإجراءات الحساسة (كما في `WORKER_DELETE_CONFIRM`/`RESTORE_CONFIRM` المعتمدتين كمرجع أسلوب). **المواصفة البصرية التفصيلية (الحركة، التوقيت، الألوان الدقيقة لكل حالة) تُترك لفريق التصميم البصري عند التنفيذ، بالالتزام بلوحة الهوية المعتمدة (`#1C351D`/`#B3CD7C`) وخط Titr.**

## 8. تبديل الحسابات (Multi-Account Switcher) — تفصيل تقني
```text
تخزين آمن محلي (مثل Android Keystore-backed storage):
 accounts: [
 { store_owner_id, phone, display_name, access_token, refresh_token, last_active_at },
...
 ]
 active_account_id: "..."
```
- التبديل = تغيير `active_account_id` فقط + إعادة تحميل البيانات المحلية. **قرار معتمد (R-35):** بيانات كل حساب معزولة تماماً على الجهاز — قاعدة بيانات/حاوية مستقلة لكل حساب، لا تختلط بيانات حسابين ولا يرى أحدهما بيانات الآخر.
- "تسجيل خروج من الهاتف" لحساب معيّن = حذف إدخاله من `accounts` محلياً (إبطال التوكنات محلياً؛ إبطالها على الخادم أيضاً عبر `POST /auth/logout` إن توفر اتصال).
- مخفية بالكامل عن أي عامل (لا `accounts` متعددة له أصلاً؛ عامل واحد = جلسة واحدة فقط).

## 9. دعم iOS

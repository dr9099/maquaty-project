## 1. آلية المزامنة (Sync Engine) — التصميم التفصيلي

### 1.1 متى تحدث المزامنة
- تلقائياً عند توفر إنترنت، بحد أدنى مرتين يومياً (القيمة الدقيقة تُضبط من `min_sync_interval_hours` في `system_settings` — افتراضي 6 ساعات، ويُمنع ضبطه بأكثر من 12 ساعة حفاظاً على أرضية R-26).
- عند فتح التطبيق (إن توفر اتصال فوراً).
- Background Sync صامت (لا يحجب واجهة المستخدم).

### 1.2 ماذا تحمل كل عملية مزامنة
```json
{
  "device_fingerprint": "...",
  "last_sync_version": 142,
  "pending_local_operations": [
    { "op_type": "SALE", "client_op_id": "uuid-محلي", "payload": { ... }, "created_at_local": "..." },
    { "op_type": "DAMAGED_GOODS", "client_op_id": "...", "payload": { ... } }
  ]
}
```
- `client_op_id`: معرّف UUID يُولَّد محلياً لحظة إنشاء العملية، يُستخدم لمنع التكرار إن أُعيد إرسال نفس العملية بسبب انقطاع اتصال أثناء الرفع.
- `last_sync_version`: آخر رقم إصدار مزامنة استلمه هذا الجهاز من الخادم، يسمح للخادم بإرسال فقط ما تغيّر منذ ذلك الحين (Delta Sync).

### 1.3 ترتيب معالجة الخادم لكل عملية واردة
```text
1. فحص client_op_id مقابل جدول `sync_operations` (فهرس فريد store_owner_id + client_op_id):
       سبق معالجته؟ → نعم → تجاهل، إرجاع النتيجة السابقة المخزَّنة دون إعادة تنفيذ
                    → لا → متابعة وتدوين العملية في `sync_operations` قبل التنفيذ
2. فحص حالة الحساب (مقفل؟ موقوف؟)
3. تنفيذ نفس سلسلة التحقق القياسية للعملية
4. تحديث حالة العملية في `sync_operations` بالنتيجة النهائية
```
حقل `devices.last_sync_version` هو أساس Delta Sync: الخادم يرسل فقط ما تغيّر منذ آخر إصدار استلمه الجهاز.

### 1.4 حل التعارضات (Conflict Resolution) حسب نوع البيانات

| نوع البيانات | استراتيجية الحل |
|---|---|
| عدّاد التجربة (`trial_sales_used`) | القيمة الأعلى الموثوقة تفوز دائماً؛ لا يُقبل انخفاضها |
| عمليات بيع/تالف/دفعات جديدة | لا تعارض فعلي ممكن لأنها عمليات إضافة بمعرّف `client_op_id` فريد |
| تعديل سعر/كمية صنف من أكثر من جهاز | نادر عملياً (تعديل الأصناف حصري للمالك)؛ الاقتراح الهندسي: Last-Write-Wins بناءً على `updated_at` الأحدث وقت استلام الطلب |
| إيقاف/حذف عامل من المالك بينما العامل متصل | يفوز قرار الخادم؛ العامل يُفصل عند أول اتصال تالٍ له |
| حالة اشتراك/تجربة | يفوز قرار الخادم؛ الجهاز لا يقرر هذه الحالة محلياً إلا كـ"آخر حالة معروفة" مؤقتاً |

### 1.5 استجابة الخادم لطلب المزامنة
```json
{
  "new_sync_version": 150,
  "account_status": "ACTIVE",
  "min_app_version": "1.4.0",
  "processed_operations": [
    { "client_op_id": "...", "status": "ACCEPTED", "server_id": "uuid-خادم" },
    { "client_op_id": "...", "status": "REJECTED", "error_code": "CREDIT_LIMIT_EXCEEDED" }
  ],
  "server_updates": { "items": [ ... ], "workers": [ ... ], "subscription": { ... } }
}
```
- هذه هي الصيغة المعتمدة الوحيدة (العقد الموحّد في `API_SPEC.md` يطابقها).
- عملية بيع مرفوضة بسبب `CREDIT_LIMIT_EXCEEDED` أو `INSUFFICIENT_STOCK` تُحفظ إضافياً في `rejected_transactions` وتظهر للمالك حصراً في شاشة `REJECTED_TRANSACTIONS` لمعالجتها (شاشة 28) — وتبقى ظاهرة للجهاز بحالة `REJECTED` في `processed_operations`.
- أي فشل آخر (ومنه `DAMAGED_GOODS` مرفوضة لنقص مخزون) لا يُحفظ للمعالجة الإدارية؛ يظهر للجهاز بحالة `REJECTED` ويُعالَج محلياً (إعادة محاولة عند توفر الكمية مثلاً) — التالف لا يُعرض على المالك للموافقة، وبقاء وصول المالك لسجلاته للاطلاع.
- `min_app_version`: إن كانت نسخة التطبيق أقدم يمنع الاستخدام ويطلب التحديث (إجبار تحديث عن بُعد).

## 2. آلة حالة الاشتراك/التجربة (State Machine)

```text
┌─────────┐   المتبقي ≤ trial_warning_threshold    ┌────────────────┐
│  TRIAL  │ ──────────────────────────────────────▶ │ TRIAL_WARNING   │
└─────────┘                                           └────────────────┘
     │                                                        │
     │ trial_sales_used = trial_sales_limit                  │ نفس الشرط
     ▼                                                        ▼
┌────────────────┐
│ TRIAL_EXPIRED   │
└────────────────┘
     │ App Owner يفعّل اشتراك
     ▼
┌─────────┐    expires_at يصل     ┌──────────┐
│ ACTIVE  │ ─────────────────────▶ │ EXPIRED  │
└─────────┘                        └──────────┘
     ▲                                   │
     └───────── App Owner يجدد الاشتراك ──┘

(مستقل تماماً عن كل ما سبق)
┌──────────┐  App Owner يوقف الحساب يدوياً  ┌────────────┐
│ أي حالة  │ ─────────────────────────────▶ │ SUSPENDED   │
└──────────┘                                 └────────────┘
```

الانتقال من `TRIAL*` إلى `ACTIVE` ممكن مباشرة حتى لو لم تُستهلَك كل الـ100 عملية بعد.

## 3. فحص حالة الحساب عند كل طلب

```text
كل طلب API وارد (بعد المصادقة الناجحة)
      ↓
هل الحساب (Store Owner الأب، إن كان الطالب عاملاً) status IN (TRIAL_EXPIRED, EXPIRED, SUSPENDED)؟
      │
      ├─ نعم → 423 ACCOUNT_LOCKED (reason حسب الحالة) فوراً
      │
      └─ لا → هل الطالب عامل وstatus=SUSPENDED/DELETED؟
                │
                ├─ نعم → 423 ACCOUNT_LOCKED (reason=WORKER_SUSPENDED)
                └─ لا → متابعة التنفيذ الطبيعي
```
هذا الفحص يحدث في كل طلب، وليس مرة واحدة عند تسجيل الدخول فقط. كود `423 ACCOUNT_LOCKED` موحّد في كل المسارات (عند الدخول وبقية الطلبات) مع `reason` يحدد الحالة الدقيقة ويوجّه التطبيق لشاشة 21 أو 24.

## 5. منطق التحقق من سعر البيع الاضطراري

```text
POST /sales مع is_emergency_sale=true
      ↓
جلب items.emergency_price_mode + الحقول المرتبطة لذلك الصنف
      ↓
   mode = COST_ONLY؟
      └─ emergency_override_price == items.cost_price بالضبط؟ لا → رفض
   mode = COST_PLUS؟
      └─ emergency_override_price >= items.cost_price + (plus_fixed أو cost_price×plus_percent)؟ لا → رفض
   mode = RANGE_OR_OPEN؟
      └─ emergency_price_min محدد؟ → emergency_override_price >= min؟ لا → رفض (400 EMERGENCY_PRICE_BELOW_MINIMUM)
      └─ emergency_price_max محدد؟ → emergency_override_price <= max؟ لا → رفض (400 EMERGENCY_PRICE_ABOVE_MAXIMUM)
      └─ كلاهما NULL (مفتوح بالكامل) → قبول أي سعر
      ملاحظة: الحدان يُفحصان كلٌّ على حدة — ترك الحد الأدنى فارغاً في النمط المفتوح لا يُلغي فحص الحد الأقصى إن حُدد.
      ↓ (قبول)
price_difference_loss = GREATEST(0, (items.sell_price - emergency_override_price) × quantity)
      ↓
متابعة معالجة البيع العادية (خصم مخزون مع القفل، قيد محاسبي + قيد خسارة منفصل إن loss > 0)
```

## 6. التحكم بالتزامن ومنع البيع الزائد

```text
POST /sales (أو /damaged-goods) يصل للخادم
      ↓
BEGIN TRANSACTION
      ↓
SELECT quantity FROM items WHERE id = :item_id FOR UPDATE
      ↓
quantity_متاحة >= quantity_المطلوبة؟
      │
      ├─ لا → ROLLBACK، إرجاع 409 INSUFFICIENT_STOCK فوراً
      │
      └─ نعم → UPDATE items SET quantity = quantity - :requested ...
               إنشاء sales/damaged_goods + ledger_entries
               COMMIT TRANSACTION
```
مثال توضيحي: صنف متبقيه 100 جرام، عاملان يحاولان بيع كامل الكمية في نفس اللحظة تقريباً. الطلب الذي يصل فعلياً أولاً لقاعدة البيانات ويحصل على القفل يُنفَّذ ويُصفِّر الكمية؛ الطلب الثاني يُرفض فوراً بـ `409 INSUFFICIENT_STOCK` دون أي احتمال لبيع نفس الكمية مرتين. ينطبق المبدأ نفسه على أي عمليتين متزامنتين تخصمان من نفس صف `items`.

## 7. قيود الإقفال المحاسبية التلقائية (عند اعتماد الإغلاق اليومي — R-21)

عند `POST /daily-closings/{id}/approve` يُنشأ تلقائياً قيد إقفال (reference_type=`CLOSING`) من مرحلتين:

**المرحلة 1 — قيد تسوية فرق الصندوق** (حسب قيمة `difference` لذلك الإغلاق):

| الحالة | مدين | دائن |
|---|---|---|
| مطابقة (difference = 0) | لا قيد تسوية | — |
| عجز (difference < 0) | `5600 عجز الصندوق` بقيمة العجز | `1000 الصندوق` |
| زيادة (difference > 0) | `1000 الصندوق` بقيمة الزيادة | `4300 فائض الصندوق` |

**المرحلة 2 — قيد الإقفال الدوري** (لكل إغلاق معتمد، على مستوى الحساب/اليوم المعتمد): تصفير حسابات النتيجة المؤقتة المتعلقة بنشاط ذلك اليوم (المبيعات `4000`، تكلفة البضاعة المباعة `5000`، مصروف الأجور `5100`، الإيجار `5200`، الخدمات `5300`، التالف `5400`، خسائر البيع الاضطراري `5450`، عجز الصندوق `5600`، فائض الصندوق `4300`) إلى حساب الأرباح المحتجزة `3900` — بحيث يصبح رصيد كل حساب مؤقت صفراً بعد الإقفال ويظهر صافي أثر اليوم في `3900`.

**قواعد ملزمة:**
- القيدان يُنشآن ضمن نفس المعاملة الذرّية مع تحويل `status=CLOSED` — نجاح أحدهما بلا الآخر مستحيل.
- بعد الاعتماد يرفض الخادم أي تعديل أو إضافة لعمليات ذلك الحساب/اليوم بـ `409 DAY_ALREADY_CLOSED` (فرض إغلاق BR-029 على مستوى الخادم).
- القيود Append-only وفق BR-055، ورصيد كل قيد متوازن (مدين = دائن) وفق BR-054.

## 8. القيود المحاسبية ومحرك تكلفة المشتريات والموردين (R-38..R-43)

### 8.1 القيود المحاسبية المزدوجة للمشتريات والموردين
| العملية | `reference_type` | الطرف المدين | الطرف الدائن |
|---|---|---|---|
| رصيد افتتاحي لمورد | `SUPPLIER_OPENING_BALANCE` | `3000 رأس المال` | `2000 الموردون / الذمم الدائنة` |
| فاتورة شراء نقدية | `PURCHASE` | `1300 المخزون` (صافي الإجمالي) | `1000 الصندوق` |
| فاتورة شراء بمحفظة | `PURCHASE` | `1300 المخزون` | `11xx المحفظة المحددة` |
| فاتورة شراء آجلة | `PURCHASE` | `1300 المخزون` | `2000 الموردون / الذمم الدائنة` |
| فاتورة شراء دفع جزئي | `PURCHASE` | `1300 المخزون` (الإجمالي) | `1000/11xx` (المدفوع) + `2000` (المتبقي) |
| إلغاء فاتورة شراء | `PURCHASE_VOID` | عكس كامل الدائنين (`1000`/`11xx`/`2000`) | `1300 المخزون` |
| سند سداد لمورد | `PURCHASE_PAYMENT` | `2000 الموردون / الذمم الدائنة` | `1000 الصندوق` أو `11xx المحفظة` |
| مرتجع مشتريات | `PURCHASE_RETURN` | `2000 الموردون` (خصم دين) أو `1000 الصندوق` (استرداد نقدي) | `1300 المخزون` |

### 8.2 خوارزمية احتساب التكلفة المتوافقة مع صلاحية القات (24–48 ساعة)
1. **حساب تكلفة الوحدة الأساسية المحوَّلة:** `effective_base_unit_cost = total_line_cost_allocated / (quantity × conversion_factor)`.
2. **يوم جديد أو رصيد مخزون صفري (`existing_qty == 0`):** يُعتمد `effective_base_unit_cost` مباشرة دون تعارض.
3. **نفس اليوم مع وجود رصيد متبقٍ (`existing_qty > 0`) وسعر مختلف:**
   - `WEIGHTED_AVERAGE`: `((existing_qty × old_cost) + (added_base_qty × new_cost)) / (existing_qty + added_base_qty)`.
   - `LAST_PRICE`: `new_cost` مباشرة لكامل الرصيد.
   - `FIFO`: تُنشأ طبقة في `purchase_items.remaining_fifo_qty`، وعند البيع تُستهلك الطبقات الأقدم أولاً ويُسجَّل مجموع تكلفتها الفعلي في `sales.cogs_amount`، ويتحدث `items.cost_price` تلقائياً لتكلفة أقدم طبقة متبقية لضبط الحد الأدنى للبيع الاضطراري.

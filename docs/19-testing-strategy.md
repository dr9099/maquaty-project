# 19 — Testing Strategy

---

## 1. مستويات الاختبار

| المستوى | النطاق | أولوية خاصة |
|---|---|---|
| Unit Tests | منطق الأعمال المعزول: حساب `credit_limit`، قيود القيد المزدوج، منطق سياسة البيع الاضطراري ، حالة آلة الاشتراك | عالية — هذه القواعد تحكم المال مباشرة |
| Integration Tests | تدفقات API كاملة: `POST /sales` بكل فروعه (نقد/إلكتروني/آجل/اضطراري)، المزامنة (`POST /device/sync`)، تفعيل اشتراك | عالية |
| Concurrency Tests | **(إلزامية)** سيناريو بيع متزامن لعاملين على نفس الصنف بكمية محدودة؛ التحقق أن طلباً واحداً فقط ينجح والآخر يُرفض بـ `409 INSUFFICIENT_STOCK` | حرجة، تمنع خسارة مالية فعلية (Over-selling) |
| End-to-End (E2E) | تدفقات `USER_FLOWS.md` كاملة على جهاز/محاكي أندرويد فعلي، بما فيها سيناريوهات Offline→Online | عالية |
| Security Tests | IDOR (محاولة وصول عامل لبيانات متجر/عامل آخر)، Rate Limiting على تسجيل الدخول، رفض استيراد نسخة احتياطية لا تطابق `tenant_binding_hash` | حرجة |
| Regression على القواعد الحاكمة | كل قاعدة في `00-RESOLVED-DECISIONS.md` (R-01 إلى R-35) يقابلها سيناريو اختبار صريح واحد على الأقل يمنع أي كسر مستقبلي غير مقصود لها | **إلزامية** (جدول قاعدة → سيناريو) |

## 2. سيناريوهات حرجة يجب تغطيتها صراحة
- تجاوز سقف الائتمان → رفض تام (Hard Block۔).
- بيع متزامن يتجاوز المخزون → رفض الطلب الثاني.
- انتهاء تجربة المالك أثناء جلسة عامل مفتوحة → فصل فوري عند أول طلب تالٍ (القسم 3 في `12-business-logic.md`).
- استيراد نسخة احتياطية لحساب مختلف → رفض قطعي.
- محاولة عامل عادي الوصول لـ `CREDIT`/`FUNDS`/`BACKUP_RESTORE` مباشرة عبر API (تجاوز الواجهة) → `403` من الخادم نفسه، وليس فقط إخفاءً في الواجهة.
- ترقية عامل مسؤول جديد مع وجود مسؤول سابق بلا تأكيد → رفض (`409`)؛ مع تأكيد → نقل ذرّي ناجح.
- **المرتجعات (R-20):** مرتجع نفس اليوم ينجح؛ مرتجع لعملية يوم سابق → `400 RETURN_DAY_PASSED`؛ بعد اعتماد اليوم → `409 DAY_ALREADY_CLOSED`؛ عامل يرتجع عملية غيره → `403 NOT_OWN_SALE`؛ كمية أكبر من المباع → `400 RETURN_QUANTITY_EXCEEDED`.
- **العمليات المرفوضة (R-30):** رفض بيع بسبب `CREDIT_LIMIT_EXCEEDED` و`INSUFFICIENT_STOCK` يُحفظ PENDING ويظهر للمالك؛ الخيارات الخمسة كلها بمساراتها وخيار خارج سببه → `400 DISALLOWED_RESOLUTION_ACTION`؛ التالف المرفوض لا يُحفظ إدارياً ويعود للجهاز.
- **تبديل الحسابات (R-31/R-35):** عزل بيانات كل حساب محلياً على الجهاز — التبديل لا يكشف بيانات متجر لعاملٍ أو متجرٍ آخر، وخروج حساب لا يمس الآخر.
- **موافقة إنشاء العامل (R-33):** إنشاء عامل عادي دون رصيد → `403 WORKER_LIMIT_REACHED`؛ بعد المنح ينجح؛ الموقوف يُحتسب والمحذوف يفتح مكاناً؛ العامل المسؤول يُنشأ دون رصيد.
- **إعادة إرسال عملية بنفس `client_op_id`** → لا تنفَّذ مرتين (فهرس `sync_operations` الفريد).
- **إغلاق اليوم:** قيود الإقفال للعجز/الزيادة/المطابقة صحيحة ومتوازنة؛ أي تعديل بعد الاعتماد → `409 DAY_ALREADY_CLOSED`.
- **عدّاد التجربة:** يزيد في `TRIAL` و`TRIAL_WARNING` حتى الحد؛ لا يقبل انخفاضاً غير منطقي عند المزامنة.

## 3. بيئة الاختبار
قاعدة بيانات اختبار معزولة تماماً عن الإنتاج، بيانات تجريبية (Seed Data) تغطي: مالكاً بعامل مسؤول وعامل عادي، أصنافاً بسياسات بيع اضطراري مختلفة الأنماط الثلاثة، عميل آجل قريباً من سقف ائتمانه.

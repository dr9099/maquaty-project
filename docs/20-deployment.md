# 20 — Deployment

---

## 1. مكونات تحتاج نشراً منفصلاً

| المكوّن | ملاحظات |
|---|---|
| Central Backend Server | API + Sync + كل الخدمات الداخلية (`05-system-architecture.md`) |
| PostgreSQL | قاعدة بيانات مركزية، نسخ احتياطية تشغيلية دورية مشفَّرة (`04-non-functional-requirements.md` القسم 10) |
| File Storage | مرفقات الإيداع، صور التالف، نسخ احتياطية سحابية، ملفات تقارير مولَّدة |
| Admin Portal (ويب) | يمكن نشره مستقلاً عن الموقع العام، بنطاق فرعي مختلف ومعزول أمنياً |
| الموقع العام (ويب) | استضافة بسيطة منفصلة تماماً، لا تشارك بيانات اعتماد مع الباقي |
| تطبيق Android | توزيع APK مباشر في البداية (حسب الموقع العام، `10-website.md`)؛ النشر عبر Google Play قرار تجاري لاحق خارج نطاق هذه الوثائق |

## 2. بيئات التشغيل (Environments)
- **Development** — بيانات وهمية، كل الحمايات مفعَّلة لكن بسجلات تفصيلية أوسع.
- **Staging** — نسخة مطابقة للإنتاج لاختبار E2E قبل الإصدار.
- **Production** — البيئة الحقيقية، أقل مستوى تفصيل في السجلات العامة، كل حمايات `13-authentication-security.md` مفعَّلة كاملة بلا استثناء.

## 3. قائمة تحقق قبل أي إصدار جديد (Release Checklist) — مقترح عملي
- كل اختبارات `19-testing-strategy.md` ناجحة (خصوصاً اختبارات التزامن والأمن).
- لا أسرار مكشوفة في الكود (Secret Scanning — `13-authentication-security.md` القسم 13).
- ترحيل قاعدة البيانات (Migration) مُختبَر على Staging أولاً، مع خطة تراجع (Rollback) واضحة.
- إمكانية إجبار تحديث التطبيق عن بُعد جاهزة وتعمل (لمعالجة ثغرة حرجة مستقبلية عند الحاجة) — **الآلية الموثقة:** الخادم يُرسل `min_app_version` في استجابة `POST /device/sync` (القيمة من `MIN_SUPPORTED_APP_VERSION` في `21-environment-configuration.md`)، والتطبيق الأقدم يمنع الاستخدام ويطلب التحديث.

## 4. آلية ترحيل قاعدة البيانات (Migrations)
كل تغيير بنيوي (مثل `is_responsible`, `max_workers_allowed`, `temp_password_hash`, جدول `rejected_transactions`...) يُدار عبر **Prisma Migrate** (حزمة Backend المعتمدة NestJS + Prisma — النقطة 13 مغلقة) مع ترقيم تسلسلي، وليس تعديلاً يدوياً مباشراً على قاعدة الإنتاج.

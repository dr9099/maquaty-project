## 1. تسجيل مالك متجر جديد وبدء التجربة المجانية

```text
فتح التطبيق لأول مرة
      ↓
شاشة LOGIN → رابط "إنشاء حساب جديد"
      ↓
شاشة SIGNUP: الاسم الكامل + اسم المحل + رقم الجوال + كلمة مرور ×2
      ↓
POST /auth/register-store-owner (يُرفق device_fingerprint تلقائياً من التطبيق)
      ↓
الخادم: يتحقق فريدية الهاتف + يفحص devices.trial_consumed لهذا الجهاز
      │
      ├─ الجهاز استهلك تجربة سابقاً → 403 DEVICE_TRIAL_ALREADY_CONSUMED
      │        ↓
      │   رسالة للمستخدم: هذا الجهاز لا يستحق تجربة جديدة، تواصل مع 735717710
      │
      └─ جهاز جديد → إنشاء store_owners (status=TRIAL, trial_sales_used=0)
               ↓
          إرجاع access_token + refresh_token
               ↓
          الانتقال تلقائياً إلى شاشة HOME
```

## 2. تسجيل الدخول (مالك أو عامل)

```text
شاشة LOGIN: رقم الجوال + كلمة المرور
      ↓
POST /auth/login (مع device_fingerprint)
      ↓
الخادم يتحقق البيانات، ثم يفحص بالترتيب (المالك أولاً — موحّد):
  1) هل الحساب موجود وكلمة المرور صحيحة؟ لا → 401 INVALID_CREDENTIALS
  2) هل حالة المالك (أو Store Owner الأب إن كان الطالب عاملاً) = TRIAL_EXPIRED أو EXPIRED أو SUSPENDED؟
         نعم → 423 ACCOUNT_LOCKED (reason حسب الحالة) → شاشة ACCOUNT_LOCKED
  3) إن كان الطالب عاملاً: هل status = SUSPENDED؟ نعم → 423 ACCOUNT_LOCKED (reason=WORKER_SUSPENDED) → بطاقة حمراء في LOGIN
  4) هل الدخول عبر كلمة مرور احتياطية مؤقتة؟
         نعم → must_change_password=true → شاشة SET_NEW_PASSWORD
      ↓ (كل الفحوصات ناجحة)
200 OK + access_token + refresh_token + account_status
      ↓
الانتقال لشاشة HOME (محتوى الشاشة يُفلتَر حسب الدور والصلاحيات فوراً)
```

## 3. عملية بيع — نقد

```text
شاشة HOME → زر "بيع"
      ↓
شاشة SELL: اختيار الصنف من القائمة (المتوفرة quantity > 0 فقط)
      ↓
إدخال الكمية أو المبلغ (الحقل الآخر يُحسب تلقائياً محلياً على الجهاز)
      ↓
اختيار زر الدفع "نقد" → ضغط زر "بيع"
      ↓
Bottom Sheet تأكيد: "شامي · 2 كيلو · 6,000 نقداً" + تأكيد/إلغاء
      ↓ (تأكيد)
   هل يوجد اتصال إنترنت الآن؟
      │
      ├─ لا → حفظ محلي فوري (SQLite) + خصم المخزون محلياً + زيادة عدّاد التجربة المحلي
      │        ↓ (لاحقاً عند توفر إنترنت، ضمن مزامنة دورية)
      │   POST /device/sync يرفع العملية إلى الخادم
      │
      └─ نعم → POST /sales مباشرة
               ↓
          الخادم يقفل صف الصنف ذرّياً، يتحقق المخزون الكافي وحالة الحساب
               │
               ├─ المخزون غير كافٍ → 409 INSUFFICIENT_STOCK
               └─ نجاح → 201 + تحديث المخزون + قيد محاسبي + زيادة trial_sales_used طالما دون الحد
                        ↓
                   رسالة نجاح + تصفير حقول الشاشة للعملية التالية
```

## 4. عملية بيع — إلكتروني، آجل، واضطراري

**إلكتروني:**
```text
اختيار زر "إلكتروني" → حقل اختيار المحفظة + منطقة رفع صورة الإيداع
      ↓
رفع الصورة (زر "بيع" يبقى معطّلاً حتى اكتمال الرفع)
      ↓
تأكيد → POST /sales مع wallet_id + deposit_attachment_url إلزاميين
      ↓ (الخادم)
نقص أي منهما → 400 MISSING_DEPOSIT_ATTACHMENT
```

**آجل:**
```text
اختيار زر "آجل" (يظهر فقط إن كان المستخدم مالكاً أو العامل المسؤول)
      ↓
اختيار عميل من القائمة، أو "عميل جديد" → فورم مصغّر → POST /credit-customers أولاً
      ↓
تأكيد البيع → POST /sales مع credit_customer_id
      ↓ (الخادم)
حساب: مجموع ديون العميل الحالية + amount، مقارنة بـ credit_limit
      │
      ├─ تجاوز (و credit_limit محدد) → 409 CREDIT_LIMIT_EXCEEDED — لا حفظ، لا خصم مخزون
      │
      └─ ضمن الحد → نجاح، تُسجَّل العملية CREDIT عادية
```

**اضطراري:**
```text
أي بائع (مالك أو عامل) يفعّل مفتاح "بيع اضطراري" ضمن شاشة البيع
      ↓
حقلا الكمية والسعر يصبحان قابلين للتعديل اليدوي + يظهر حقل "سبب التعديل" الإلزامي
      ↓
تأكيد البيع → POST /sales مع is_emergency_sale=true + emergency_override_price + emergency_reason
      ↓ (الخادم)
جلب items.emergency_price_mode لذلك الصنف → السعر يحترم السياسة؟
      │
      ├─ لا → 400 EMERGENCY_PRICE_BELOW_MINIMUM — لا حفظ
      │
      └─ نعم → خصم المخزون + قيد بيع عادي
                        + قيد خسارة منفصل = (sell_price - emergency_override_price) × quantity إن موجب
                        ↓
                 العملية تظهر في OPERATIONS_LOG بشارة "بيع اضطراري" + السبب عند الضغط عليها
```

## 5. دورة حياة الاشتراك الكاملة

```text
إنشاء حساب → TRIAL (100 عملية)
      ↓ (كل عملية بيع تزيد trial_sales_used — والمتبقي المشتق يُنقص)
الرصيد المتبقي ≤ 30 عملية
      ↓
status = TRIAL_WARNING
      ↓
إشعار Push فوري + ظهور عبر أي مزامنة لاحقة
      ↓
عرض بطاقة تحذير داخل التطبيق: "تبقى X عملية. تواصل مع 735717710 [نسخ] [واتساب]"
      ↓
الرصيد = 0
      ↓
status = TRIAL_EXPIRED
      ↓
قفل كامل لكل الواجهات، المالك وكل عمّاله دفعة واحدة
      ↓
شاشة ACCOUNT_LOCKED: رسالة + رقم 735717710 + زر نسخ + زر واتساب
      ↓
صاحب المتجر يتواصل هاتفياً/واتساب مع App Owner
      ↓
App Owner في Admin Portal: GET /admin/store-owners?phone= → يجد الحساب
      ↓
POST /admin/store-owners/{id}/subscriptions (plan_id = شهر/6أشهر/12شهر/مخصص)
      ↓
الخادم: ينشئ subscriptions جديد، store_owners.status = ACTIVE
      ↓ (عند أول مزامنة لتطبيق المالك وكل عمّاله)
رفع القفل تلقائياً، عودة كل الواجهات للعمل
      ↓ (أي عامل كان SUSPENDED يدوياً قبل القفل يبقى SUSPENDED)
      ↓ (لاحقاً عند وصول expires_at)
status = EXPIRED → نفس مسار القفل أعلاه من جديد
```

## 6. إنشاء عامل وإدارة صلاحياته

```text
HOME (المالك) → WORKERS_LIST → زر "+ إضافة عامل"
      ↓
شاشة WORKER_ADD: الاسم + رقم الجوال + كلمة مرور ×2 + ضبط 5 مفاتيح صلاحيات
      ↓
POST /workers
      ↓
الخادم يتحقق فريدية الهاتف عالمياً ورصيد موافقات العمال العاديين (R-33 — العامل المسؤول يُنشأ دون رصيد)
      │
      ├─ مكرر → 409 PHONE_ALREADY_EXISTS
      ├─ لا رصيد موافقات كافٍ → 403 WORKER_LIMIT_REACHED (رسالة إرشاد بالتواصل مع App Owner للمنح من Admin Portal)
      └─ نجاح → 201، العامل الجديد يظهر في WORKERS_LIST فوراً

[لاحقاً] المالك يضغط على عامل من القائمة → WORKER_EDIT
      ↓
تعديل صلاحية/كلمة مرور، أو تفعيل مربع "إيقاف الحساب مؤقتاً"
      ↓ (عند تفعيل الإيقاف)
PATCH /workers/{id}/suspend { suspended: true }
      ↓
الخادم: workers.status = SUSPENDED
      ↓ (عند أي محاولة دخول تالية)
رفض فوري + عرض شاشة LOGIN بحالة "حساب موقوف"

[أو] المالك يضغط "حذف الحساب" → WORKER_DELETE_CONFIRM → تأكيد
      ↓
DELETE /workers/{id}
      ↓
العامل يختفي من WORKERS_LIST، سجلاته التاريخية تبقى محفوظة للتقارير والمحاسبة
```

## 7. ترقية عامل كـ"مسؤول"

```text
المالك → WORKER_EDIT لعامل معيّن → زر "تفعيله كمسؤول"
      ↓
POST /workers/{id}/promote-responsible
      ↓ (الخادم)
يوجد عامل مسؤول آخر حالياً؟
      │
      ├─ نعم → 409 RESPONSIBLE_WORKER_EXISTS + بيانات العامل الحالي
      │        ↓
      │   التطبيق يعرض شاشة RESPONSIBLE_WORKER_CONFLICT_CONFIRM
      │        ↓ (تأكيد)
      │   POST /workers/{id}/promote-responsible { confirm_replace: true }
      │        ↓
      │   عملية ذرّية: القديم is_responsible=false + الجديد is_responsible=true
      │
      └─ لا يوجد مسؤول حالياً → تفعيل مباشر بلا تأكيد إضافي
      ↓
العامل الجديد يحصل فوراً على وصول: الآجل، الأموال، العمال المدارين، النسخ الاحتياطي
```

## 8. معالجة عملية مرفوضة

```text
المالك → شاشة REJECTED_TRANSACTIONS → GET /rejected-transactions?status=PENDING
      ↓
يفتح سجلاً مرفوضاً → يرى: المنتجات، الإجمالي، التاريخ، العامل، العميل، سبب الرفض
      ↓
يختار إجراءً حسب سبب الرفض (R-30):
   · تجاوز سقف الائتمان → ترحيل كخسائر أو قيد كدين على العميل
   · نقص المخزون → تعديل الكمية والموافقة (مع adjusted_quantity) أو قبول البيع مع رصيد سالب أو رفض نهائي
      ↓
POST /rejected-transactions/{id}/resolve { resolution_action, adjusted_quantity? }
      ↓ (الخادم)
يتحقق مطابقة الخيار للسبب (خلاف ذلك 400 DISALLOWED_RESOLUTION_ACTION)
      ↓
ينشئ القيد المحاسبي المناسب + يُقفل السجل (status=RESOLVED) + يسجّل في audit_log
```

## 10. النسخ الاحتياطي — محلي وسحابي

**محلي (تصدير):**
```text
BACKUP_RESTORE → زر "تصدير نسخة احتياطية"
      ↓
التطبيق يُصدِّر قاعدة البيانات المحلية إلى ملف maquaty-backup-YYYY-MM-DD.db (مُضمَّن فيه معرّف الحساب المشفَّر)
      ↓
يفتح مدير ملفات الجهاز → المستخدم يختار مكان الحفظ
```

**محلي (استيراد):**
```text
BACKUP_RESTORE → زر "اختيار ملف من الهاتف"
      ↓
مدير ملفات الجهاز → اختيار ملف .db
      ↓
فحص تطابق معرّف الحساب المشفَّر داخل الملف مع الحساب الحالي
      │
      ├─ لا يطابق → رفض فوري: "النسخة الاحتياطية غير تابعة لهذا الحساب"
      │
      └─ يطابق → RESTORE_CONFIRM: عرض اسم/حجم/تاريخ الملف + تحذير استبدال كامل
               ↓ (تأكيد)
          استبدال قاعدة البيانات المحلية بالكامل بمحتوى الملف المختار
```

**سحابي:**
```text
BACKUP_RESTORE → (حساب تجريبي؟ → BACKUP_PAYWALL_MODAL، إيقاف هنا)
      ↓ (حساب مشترك فعلياً)
زر "عمل نسخة احتياطية سحابية" → POST /backups/cloud
      ↓
مؤشر تقدّم → نجاح/فشل → تحديث "آخر نسخة سحابية: الآن"
      ↓ [لاحقاً، من جهاز آخر مثلاً]
GET /backups/cloud → POST /backups/cloud/{id}/restore → نفس فحص المطابقة + تأكيد صارم
```

## 12. استرجاع كلمة مرور مالك متجر منسية

```text
مالك المتجر ينسى كلمة مروره
      ↓
يتواصل خارج النظام (هاتف/واتساب) مع App Owner (735717710)
      ↓
App Owner → Admin Portal → بروفايل المالك → زر "توليد كلمة مرور احتياطية"
      ↓
POST /admin/store-owners/{id}/generate-temp-password
      ↓
الخادم يولّد كلمة مؤقتة عشوائية، يبطل أي كلمة مؤقتة سابقة
      ↓
App Owner ينسخها ويرسلها لمالك المتجر يدوياً (خارج النظام)
      ↓
مالك المتجر يفتح شاشة LOGIN العادية: رقم الجوال + الكلمة المؤقتة
      ↓
POST /auth/login → نجاح عبر الكلمة المؤقتة → 200 { must_change_password: true, temp_access_token }
      ↓
توجيه إلزامي فوري لشاشة SET_NEW_PASSWORD
      ↓
إدخال كلمة مرور جديدة + تأكيدها → POST /auth/set-new-password
      ↓
إصدار access_token/refresh_token عاديين كاملي الصلاحية → انتقال لـ HOME
```

## 14. دورة المشتريات وإدارة الموردين (للمالك حصراً — R-38..R-43)

### 14.1 إنشاء فاتورة شراء واعتمادها (مع حوار التسعير لنفس اليوم)

```text
HOME / القائمة الجانبية (المالك فقط) → المشتريات (PURCHASES) → زر "فاتورة شراء جديدة"
      ↓
اختيار مورد نشط (أو إنشاء مورد سريع) + تاريخ الفاتورة + الأصناف والكميات ووحدة الشراء ومعامل التحويل + الخصومات
      ↓
اختيار حالة الفاتورة: مسودة (DRAFT) أو ترحيل واعتماد فوري (POSTED) + طريقة الدفع (CASH / ELECTRONIC / CREDIT / PARTIAL)
      ↓ (إذا وُجدت فاتورة معتمدة سابقة لنفس الصنف في نفس اليوم أو مخزون قائم بسعر مختلف ولم تُحدد طريقة تسعير)
الخادم يُرجع 409 COSTING_METHOD_REQUIRED (أو يعرض التطبيق الحوار مسبقاً)
      ↓
نافذة حوار عربية مبسطة لاختيار طريقة احتساب التكلفة (R-40):
  1) دمج وحساب المتوسط (WEIGHTED_AVERAGE)
  2) اعتماد السعر الجديد للكل (LAST_PURCHASE_PRICE)
  3) بيع القديم بسعره أولاً ثم الجديد (FIFO) — مع استثناء القات خلال 24–48 ساعة (أحدث سعر كمرجع وعند البيع تستهلك الأقدم أولاً)
      ↓
POST /v1/purchases (أو حفظ محلي في SQLite + طابور المزامنة PURCHASE مع clientOpId)
      ↓ (نجاح الاعتماد POSTED)
توليد رقم متسلسل PUR-YYYYMMDD-NNNN داخل قفل المتجر + زيادة مخزون الأصناف وتحديث cost_price وحد البيع الاضطراري + تحديث رصيد المورد + قيد مزدوج متوازن في حساب 2000 (الموردون / الذمم الدائنة)
```

### 14.2 سداد دفعة لمورد وكشف الحساب التراكمي وتصديره

```text
SUPPLIERS → اختيار المورد → SUPPLIER_DETAIL
      ↓
عرض الرصيد المستحق + أعمار الديون (0-30، 31-60، 61-90، +90 يوماً) + كشف الحساب التراكمي الجاري
      ↓
الضغط على "تسجيل سداد للمورد" → تحديد المبلغ وطريقة السداد (CASH من الدرج أو ELECTRONIC من المحفظة + صورة الإشعار)
      ↓
POST /v1/suppliers/{id}/payments (أو طابور المزامنة SUPPLIER_PAYMENT)
      ↓
إنقاص رصيد المورد + قيد مزدوج: من حـ/ 2000 الموردون إلى حـ/ 1010 الصندوق أو 1020 المحفظة + خصم السداد النقدي من الكاش المتوقع للمالك في مطابقة اليوم
      ↓
زر التصدير: توليد ومشاركة كشف الحساب بصيغة PDF عربي منسق أو ملف جدول CSV/Excel مباشرة من الجهاز
```

### 14.3 مرتجع مشتريات مضبوط بقاعدة عدم البيع (R-41)

```text
PURCHASES → فتح فاتورة معتمدة (POSTED) → زر "تسجيل مرتجع مشتريات"
      ↓
تحديد البند والكمية المرتجعة وطريقة التسوية (DEDUCT_PAYABLE / CASH_REFUND / ELECTRONIC_REFUND) والسبب
      ↓
```
